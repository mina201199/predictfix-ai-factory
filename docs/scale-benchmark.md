# 規模壓測：上萬筆資料時的檢索與工單列表

測試日期：2026-10-15。原始資料見 [scale-benchmark.json](../artifacts/scale-benchmark.json)，重跑方式見文末。

## 結論

資料量變大時，最先撐不住的是**檢索與資料庫查詢**，不是語言模型。模型每次最多只讀 12 個候選段落，與資料庫大小無關。

修改前：每次查詢都會重建全部段落的 TF-IDF 與 BM25 索引，而且是在 `async` 函式裡同步執行，查詢期間整個服務都在等待（`/healthz` 的延遲幾乎等於查詢時間）。工單列表則是每張工單各查一次流程資料（N+1）。

修改後（同一台電腦、同一版壓測腳本，前後連續執行）：

| 段落數 | 查詢中位數 | 查詢期間其他請求最慢 | 1 萬張工單列表 | 伺服器記憶體峰值 |
|---:|---:|---:|---:|---:|
| 1,000 | 0.44s → **0.015s** | 0.44s → 0.011s | 6.8s → **0.48s** | 189 → 201 MB |
| 10,000 | 2.65s → **0.087s** | 2.66s → 0.038s | 6.7s → **0.49s** | 263 → 300 MB |
| 30,000 | 8.16s → **0.235s** | 8.99s → 0.092s | 7.1s → **0.54s** | 444 → 575 MB |

檢索排名完全不變：`scripts/evaluate_retrieval.py` 的 3 種方法、共 60 個題目，回傳段落與名次零差異；另有測試比對快取與不使用快取的結果相同。

## 改了什麼

| 位置 | 修改 |
|---|---|
| `backend/maintenance_ai.py` | 語料與索引改為快取。快取鍵是資料庫指紋：文件的 `(id, active)` 加上已發布案例的 `(id, revision)`。任何 API 或 process 匯入、撤回手冊或發布、撤回案例時，快取都會自動失效。索引依機型與合成資料條件分開保存，最多 8 組；語料改變時舊索引立即釋放 |
| `backend/maintenance_ai.py` | BM25 的文件頻率改為建索引時計算一次；`/api/assist` 的檢索改由 `run_in_threadpool` 執行，不再卡住事件迴圈 |
| `backend/app.py`、`backend/store.py` | 工單列表改用一次 `LEFT JOIN` 帶入流程資料；新增選用的 `limit`／`offset`，不帶參數時仍回傳全部，前端不受影響 |

## 限制與後續

- **第一次查詢仍然慢。** 伺服器啟動，或手冊／案例有變動後的第一次查詢需要建索引：30,000 段落約 7.6 秒。若變動頻繁，可以改成變動後在背景預先建好索引。
- **記憶體增加。** 30,000 段落時多約 130 MB，每多一組機型條件就多一份索引。多個 worker process 時，每個 process 各有一份快取。
- **仍有其他 N+1 查詢。** 人員清單（`operations.people`）、成效分析（`/api/analytics`）與派工名單（`workforce.roster`）仍逐張讀取工單流程資料，這次沒有修改。
- **匯入手冊仍是 O(N)。** 檢查重複版本時會讀取全部文件；不在查詢路徑上，但文件數很多時匯入會變慢。
- **記憶體內 TF-IDF 的極限未量測。** 本次只測到 30,000 段落。資料量再大一個數量級時，應評估資料庫全文檢索（SQLite FTS5、PostgreSQL）或獨立的搜尋服務。
- **資料是程式產生的假資料**，只能說明速度與資源，不代表檢索準確度。
- **只比較同一輪內的數字。** 同一台電腦在不同時段量到的絕對值差異可達兩倍（修改前、30,000 段落，另一次量到 4.45 秒），所以只比較同一輪內前後連續執行的結果。

## 重跑方式

```powershell
.\.venv\Scripts\python.exe scripts\benchmark_scale.py run --paragraphs 1000,10000,30000 --tickets 10000 --label after
```

腳本會為每個規模建立暫存的 SQLite 資料庫，直接寫入假手冊與工單，以 production 模式啟動 uvicorn（連接埠 8095），並關閉本機模型與 OpenAI。量測項目：
- `/api/assist` 的延遲，設定 `use_llm=false`，不指定機型，所以會檢索全部段落。
- 查詢期間另一條連線每 50ms 呼叫一次 `/healthz` 的最長延遲。
- `GET /api/tickets` 的延遲。
- 伺服器程序的記憶體峰值。

量測「修改前」時，要在修改前的程式碼上執行同一支腳本。
