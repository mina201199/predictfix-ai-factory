# 面試回答與證據（2026-10-21）

這是一套具備權限、維修流程及可追溯知識來源的本機 MVP。可展示工程能力；尚未完成真實企業介接、工廠驗收或維修效益量測。

本輪從主線 `2c9e38f` 整理面試材料，修改位於 `codex/interview-readiness`；沒有合併訓練分支或替換模型。最新訓練數據來自 `codex/qlora-collapse-fix` 的 `fc2ed2a`，選定報告的原樣副本與來源 SHA-256 見 [證據目錄](../artifacts/interview-20261021/README.md)。操作順序見 [面試展示](interview-demo.md)，交接及待提供資料見 [交接清單](interview-handoff-20261021.md)。

## 30 秒介紹

> 我做的是維修流程與知識查找的輔助系統。工程師先記錄異常，系統依機型找出可追溯的手冊與案例，由主管核准排查清單及派工；工程師提交量測和復測結果，再由主管審核結案。模型只協助選取來源，權限和狀態轉換由後端控制。目前已完成本機功能與隔離測試，真實工廠介接和節省時間仍待現場驗證。

## 主管和 user 怎麼分權

這裡的 user 是維修工程師，尚無獨立報修員、稽核員或企業管理員角色。

| 操作／資料 | 工程師 | 主管 |
|---|---|---|
| 工單看板 | 同廠共用，可看他人工單 | 可看全廠工單 |
| 開始維修、填驗收結果、工時、照片、提交完工 | 限自己被指派的工單 | 不能代替負責工程師執行這些操作 |
| 派工、核准清單、審核結案 | 不允許 | 允許 |
| 人員負荷、出勤與派工推薦 | 不允許 | 允許 |
| 帳號、手冊、案例發布、圖譜審查、介接管理 | 不允許 | 允許 |
| 有效手冊、已發布案例、已核准有效圖譜 | 可查詢 | 可查詢並管理 |
| 他人工時、全廠統計、領料紀錄 | 目前仍可讀取 | 可讀取 |

> 我用三層規則：RBAC 決定能做哪些操作，工單歸屬決定能操作哪張單，再把工程師提交和主管審核分開。這些檢查在 API 後端執行，不依賴前端按鈕。角色由登入 session 決定，模型不能替自己取得權限或核准結案。

登入另有密碼雜湊、session 撤銷、CSRF、Origin 檢查與失敗節流。權限矩陣測試以未登入、主管、工程師及非負責工程師呼叫端點。詳見 [完整權限矩陣](access-control.md)。

**必須主動說明的邊界：** 同廠共用看板是目前設計，不能說工程師只能「看到」自己的工單。主管同時能管理帳號及審核，還不是嚴格企業職責分離；尚無 SSO、多租戶隔離，登入節流也未跨程序共用。稽核紀錄不是不可竄改的外部存證。

## CPU、GPU 與微調

### 日常服務的量測

**本機現場實跑補充（2026-10-21）：** 已啟動同一 Gemma Q8_0，在 AI 中心完成真正模型選段與原文核對。第一次查詢 10.47 秒，同題重跑約 3.3–3.5 秒；context 8192、CPU 12 執行緒，不能直接套用下方舊簡短題目約三秒的結論。見 [現場證據](../artifacts/interview-gemma-live-20261021/README.md) 與 [啟動方式](interview-gemma-live.md)。

現行預設為 Gemma 4 E2B Q8_0，本機安裝腳本使用 llama.cpp CPU 版。以下是 **2026-10-15 既有基準**，本輪沒有重新跑模型：i5-14500、64 GB RAM、GTX 1050 Ti 4 GB，同一組 44 題原創合成選段題，單一 slot、context 2048。

| 模式 | 延遲中位數 | P95 | 程序記憶體峰值 | 選段完全正確 |
|---|---:|---:|---:|---:|
| CPU，12 執行緒 | 2.94 秒 | 3.57 秒 | 2,600 MB | 44/44（100%） |
| GPU，32/36 層卸載 | 0.98 秒 | 1.37 秒 | 2,890 MB | 43/44（97.7%） |

GPU 組另記錄 2,418 MB 顯存；它與程序 RAM 是不同指標。來源：[基準表與方法](local-llm-benchmark.md)、[原始報告](../artifacts/local-llm-benchmark.json)。

> 我不是因為完全沒有 GPU 才用 CPU。這個小模型的選段任務，CPU 在既有測試中約三秒可完成，所以日常服務可不配置專用推論 GPU；有較高即時性需求時再評估 GPU。這是單機合成基準，不是多人並發 SLA，也還沒有成本或耗電的實測比較。

### QLoRA 的成果與失敗

**有做 GPU 訓練，但尚未採用微調後模型。** 2026-10-20 在 GTX 1050 Ti 4 GB 上完成 504 步，CPU 放 embedding／PLE／lm_head，GPU 使用 NF4 decoder。PyTorch peak allocated 為 **1,784 MiB**、peak reserved 為 **2,084 MiB**，CPU peak working set 為 **10,582.46 MiB**。配置器高水位不是整張卡的獨占實體顯存，不能據此宣稱顯存或成本降低百分比。

新 100 題合成測試使用相同 NF4 與受限解碼條件比較：

| 指標 | 未微調 NF4 基準 | 504 步 QLoRA |
|---|---:|---:|
| 完全正確率 | 18% | 42% |
| 段落 precision | 42.29% | 73.33% |
| 段落 recall | 90.77% | 50.77% |
| 空金標正確拒答 | 0/30 | 18/30 |
| 三段答案完全正確 | 14/20 | 0/20 |

> 微調後比較少亂選，但多段答案嚴重漏選，總分增加不能掩蓋召回下降。我保留原服務模型，先分析模型在候選順序與停止選段上的問題，而不是直接上線。

資料為同一助理建立的合成題，沒有外部維修專家盲測。28 題開發驗證的 85.71% 不能當新情境驗收；也不能把這裡的 100 題 NF4 結果與前述 44 題 Q8_0 結果當同條件比較。完整指標見 [100 題原始比較](../artifacts/interview-20261021/selection-independent-v5-comparison-20261020.json)、[訓練原始紀錄](../artifacts/interview-20261021/qlora-coverage-train-20261020.json)。

## 工單是從哪裡來的

目前支援人工報修、外部 API 及 CSV；外部端實測對象是本機模擬器，尚非企業 MES／ERP。

> 外部系統傳來源、工單 ID、事件 ID、版本、機台代號與症狀。我先驗 HMAC 與時間窗，再檢查事件重送及版本順序；機台對應成功才建立待指派工單，未知機台保留待處理，不能由外部直接指定主管權限或結案。內部狀態變更在同筆交易寫入 outbox，再由背景 worker 回傳；失敗會退避重試，超過上限由主管處理。

回寫是至少一次傳遞，接收端要依事件 ID 去重，不能說 exactly-once。主線已包含正式 Compose 的 worker 與 PostgreSQL 事件鎖定；2026-10-20 的 [稽核紀錄](../artifacts/system-audit-20261020/README.md) 有 PostgreSQL 介接測試證據。本輪只做隔離 SQLite／本機 HTTP，沒有再驗收企業網路或 PostgreSQL。完整契約見 [介接文件](ticket-integration.md)。

## 知識圖譜與資料處理

> 手冊、案例先依來源、機型與版本管理；圖譜把警報、零件、步驟、備品和資格的關係留下逐字引文，經主管核准才供查詢。來源撤回或改版後相關關係失效，查詢只沿有界的有效路徑，不把有連結解讀為診斷正確。

固定合成評估含 12 題檢索與 2 題權限情境。8 題有相關來源的題目，macro recall 由 84.38% 變成 100%；7 題可答題取得完整 required 來源的比例由 71.43% 變成 100%。這是同一 top-5 基準加圖譜路徑後的**文件集合覆蓋**，不是相同 k 的排名比較，也不是診斷正確率。

圖譜有獨立 `graph.html`、`/api/graph/assist`，目前一般 `/api/assist` 尚未直接接入圖譜。不能說每次 AI 回答都經過圖譜，也沒有自動抽取所有語意關係。真實資料、專家核對和大規模資料仍待驗證。詳見 [圖譜文件](knowledge-graph.md)。

## 為什麼不再用 Qwen

> 現行預設已改成 Gemma；Qwen 留作歷史對照。選型同時考慮既有選段基準、模型來源與客戶採購政策，實際案場合規仍需依客戶規定確認。

不把「避開中國來源模型」說成已取得所有台灣案場的合規認證。舊 Qwen CPU LoRA、Gemma QLoRA 與現在的 Gemma Q8_0 服務是不同實驗／部署狀態。選配 OpenAI 會有外送路徑；本機面試設定使用 `OPENAI_ENABLED=0`，完整斷網驗收尚未完成。詳見 [模型選型](model-selection.md)。

## 業務價值怎麼說

| 現有能力 | 可說明的流程價值 | 不能直接宣稱 |
|---|---|---|
| 工單附來源、版本、核准清單與復測證據 | 主管可以追查為什麼這樣處理、誰核准、驗收依據是什麼 | 已滿足所有企業稽核要求 |

| 發布經核對的維修案例 | 後續可以檢索已確認的處置紀錄 | 知識完整或維修成功率已提升 |

需要使用者提供：目前簡報、展示方式與設備，以及實際報修／派工／查資料／驗收流程。正式上線工作另立範圍，本輪未執行。
