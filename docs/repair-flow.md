# 維修流程、定期保養與備品

更新：2026-10-06。入口 `/workflow.html`，展示與正式模式共用，沿用後端登入、CSRF 與主管／工程師權限。

## 從報修到案例

1. 選設備並填症狀，查找適用來源。條件、警報、近期變更、影響範圍與已查項目未填時顯示補問。補問採結構化欄位檢查，本機 AI 沿用已驗證的來源段落選取，沒有新增故障診斷模型。
2. 建立待指派工單，補問資訊一併保存。之後可從工單「補充報修條件」繼續填寫；修改保留歷程。已核准清單的機型不能透過補問更換。
3. 比較候選手冊／已發布案例的原文、機型與版本。這些是排查依據，尚非自動產生的維修方案。資格、工時、工具、備品及驗收標準由主管確認，不補造文件未提供的數值。
4. 主管選來源，編排清單。每張清單最多 16 項，至少一項排查、一項驗收；每項必填判定依據。可以引用來源，也可以建立標示為主管自訂的項目。引用時後端核對來源仍有效、機型與來源雜湊；核准後保存來源原文快照與核准人。
5. 主管填剩餘估時與必要資格，透過 `/api/dispatch` 推薦。出勤、资格與剩餘容量不符者不提供指派按鈕。正式模式的派工 API 再次核對資格與容量。展示模式既有其他入口仍保留原展示派工規則。
6. 指派工程師開始維修，逐項保存通過／未通過／不適用與實際結果。驗收項目不可不適用；排查不適用須填原因。保存失敗結果不會結案，可繼續排查。
7. 排查項目需通過或有不適用說明，所有驗收需通過，才可提交結果。量測 CSV、照片、實際工時沿用既有功能。提交保存當時的完整清單／來源／結果快照，主管核對後通過或退回。
8. 退回重修會清除當前逐項結果，要求重新確認；前次結果保留於提交歷程。清單修改有版本衝突檢查，核准新版保留舊版並清除當前結果。
9. 主管從已完成工單建立案例草稿，預填已記錄的機型、條件、發現與驗收文字。原因仍待人員確認。只有人工核對發布的案例進入檢索。

未附清單的既有工單保留原本提交規則，不會把歷史案件自動變成已核准的排查程序。系統結案不代表自動核准復機或生產。

## 定期保養

主管建立設備、機型、保養名稱、天數週期、首次到期日與自訂排查／驗收項目。

- 日期以台灣時區計算；介面顯示今天到期、逾期、七日內到期與已建立工單。
- 由主管按「建立到期工單」；同一計畫只有一張進行中工單，重複點擊返回既有工單。
- 未到期或已停用的計畫不能生成新工單。停用計畫保留歷史與現有工單。
- 審核通過後，下次到期日為完成日加週期天數。退回重修不推進週期，也不建立第二張保養工單。
- 提醒是系統內到期清單與數量提示；没有外部通知、郵件、排程服務或感測運轉時數觸發。

## 備品庫存

主管先建立料號／名稱、單位與最低庫存；新增備品庫存從零開始，初始數量以入庫紀錄建立。

- 入庫限主管。領用需綁定有效且尚未提交審核的工單；工程師只能操作自己的工單，主管可代辦。
- 庫存不足拒絕領用，SQLite 將檢查與扣帳串行執行。退料不可超過同一工單／備品已領用且尚未退回的淨數量。
- 領用／退料／入庫有請求編號、操作者、時間、依據及異動後餘額。相同請求重送不重複扣帳；內容不一致回覆衝突。
- 已完成工單仍允許退回未使用備品，不允許新增領用。
- 低於最低庫存時顯示低庫存提示。未做採購、金額估算、庫位、批號、序號、領料保留或 ERP 同步。

## 資料與驗證

清單、結果、報修條件與歷程保存在既有 `ticket_workflow`。新增 `maintenance_plans`、`stock_items`、`stock_movements` 三張表；啟動採既有 `create_all` 追加，未修改舊表欄位。SQLite 備份會涵蓋新表。這不是通用 schema migration 工具。

`tests/repair_flow_scenario.py` 在獨立正式模式資料庫驗證報修、来源核准、版本衝突、資格與出勤派工、驗收阻擋、越權拒絕、並發領用、退料上限、重修歷程、案例來源、保養冪等與週期更新、重啟保存。`tests/demo_flow_scenario.py` 驗證展示版新舊來源與引用附件。測試不寫入本機正式庫。

PostgreSQL 已有後續情境與介接驗證，範圍見 [系統稽核](../artifacts/system-audit-20261020/README.md)；不能將其當成所有並發負載與企業環境皆通過。沒有企業領域驗收或 AI 診斷正確率／節省工時的評估結論。
