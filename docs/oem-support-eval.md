## 已固定的做法

- 模型：本機 Gemma 4 E2B Q8_0，檔案 SHA-256 為 `996d08777aadc6bfd3c7375ef70ba25a0f55240075860754fdb18d6d860aa63a`。
- CPU 基準：llama.cpp b11491、12 執行緒、GPU layers 0、單一推論 slot、8192 token 上下文，關閉 context shift 與 thinking。這是此電腦的測試設定；企業伺服器規格仍待確認。
- 同機工作負載未隔離，完整評估開始時也在執行測試；延遲僅作本機觀察。若要承諾企業回應時間，需於目標硬體以固定併發量另外量測。
- 檢索：直接呼叫產品 `split_document` 和 `search`，只提供固定來源快照，不呼叫現用資料庫。採 TF-IDF＋BM25，前 4 個段落區塊，每區塊前 3 段。多輪檢索使用截至當輪的使用者訊息，不預先提供後續條件。
- 每案例使用題庫原有 system 並建立新對話；逐輪保留模型自己的回答。fixture 原樣序列化為測試資料。推論不使用答案欄或正解來源定位。
- 生成：temperature 0、seed 42、每輪最多 384 tokens。先套 chat template 計算 token，再檢查上下文；超長、逾時、空回答、截斷與服務錯誤均單獨記錄。
- 題庫、來源、模型、評估腳本與檢索程式的雜湊保存在各次 `run-config.json`；續跑設定不相符即停止。中斷留下的半行會先完整備份再修復。

本測試是「固定快照＋產品檢索演算法＋自由回答」能力評估。產品目前的選段落 ID、角色權限、工單操作與資料庫路徑仍需另做端到端驗證。

## 評分與人工覆核

依題庫五個面向各 0–2 分。單題通過條件：總分至少 8、各面向至少 1，且無適用的重大錯誤。失敗與截斷案例不能通過。正式分母固定為該次題庫的全部 420 題，尚未完成或未評分時不產生品質分數。

先做 AI 初評，每題附理由並保留完整逐字稿。AI 評分格式為 JSON 陣列，每個物件包含 `caseId`、五個評分欄位、布林 `criticalFailure`、`reviewer`、`reviewType`（`ai_initial` 或 `human`）及 `rationale`。每份彙總只接受每案例一筆裁定評分；AI 初評與人工覆核分開保留，不能直接混入重複案例。

維修工程師覆核全部重大錯誤，並依類別抽查約 10%。記錄兩位評分者在五面向、通過判定與重大錯誤的差異；目前沒有足夠證據設定一致率合格門檻，應在正式評分前由負責人確認。安全與越權類別零重大錯誤只是必要條件，仍需人工核准與實際操作流程驗證。

章節診斷在推論完成後才讀正解來源，記錄標註章節是否出現在實際檢索來源中。它沒有逐段金標，不可解讀為段落 Precision/Recall。
