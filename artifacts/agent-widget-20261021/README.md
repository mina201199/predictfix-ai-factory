# 全站浮動維修 Agent 實測

日期：2026-10-21。Windows 本機展示服務 `127.0.0.1:18962`，Gemma `gemma-4-E2B-it-Q8_0` 由 `127.0.0.1:18964` 提供 CPU 推論。

## 已實際驗證

### 逐點串流更新（目前版本）

右下角維修助手使用實際模型串流；每一點建議的 JSON 物件完整且來源 ID／新增數值檢查通過，就先顯示該點。最後再顯示完整回答、可展開的來源與追問。這是逐點更新，不是逐字動畫，也不是先取得完整回答再延遲播放；原有 JSON API 回傳仍相容。

同題「PF-INTERVIEW-DEMO 新增刀具後，只有特定刀位卡住，先核對什麼？」的本機 CPU 實測：

| 版本 | 第一段顯示 | 完整回答 |
| --- | --- | --- |
| 初接串流 | 10.2 秒 | 16.0 秒 |
| 精簡提示詞 | 8.1 秒 | 12.4 秒 |
| 最終版本 | 8.4 秒 | 13.1 秒 |

這是不同提示詞的單次觀察，受輸出長度、快取與本機負載影響，不是嚴格效能比較或延遲保證。`streaming-progress.png` 記錄第一點已出現、仍在生成的畫面；`streaming-complete.png` 顯示完成後的計時與引用。

- 後端 8 項相關測試通過，見 `../agent-streaming-tests.xml`。包含來源錯誤、虛構數值、缺少機型、匿名／CSRF、草稿不執行與原本同步問答。
- ASGI 整合測試保留真實 `chat → answer → generate_json`，模型送完第一點後模擬瀏覽器斷線，確認上游 HTTP response 關閉、未送出正式 result。
- `node tests/agent_streaming_ui_test.cjs` 的 3 個情境通過：中文字元跨分包、未收到正式結果即中斷、伺服器錯誤；讀取器均會釋放。
- 中途預覽不寫入對話歷史；斷線或最終引用檢查失敗時移除預覽。建立工單與派工僅在完整結果後顯示確認卡，不串流操作參數或自動執行。

驗證方式：重新整理頁面，開啟右下角「維修助手」後輸入上述問題。應先看到第一點與「完整回覆尚未完成」，稍後補齊來源與追問；完成狀態列顯示第一段及完整耗時。

### 白話問答與等待時間更新

浮動助手改為先依機型檢索來源，再由本機 Gemma 整理一至兩點白話建議，附上 `[S1]` 等來源編號及可展開原文，並支援接續追問。知識中心原本的選段頁不在這次修改範圍。

- 問「換刀卡住怎麼辦」但未提供設備／機型，立即追問，畫面顯示 0.0 秒，不呼叫模型。
- 問「機型是 PF-INTERVIEW-DEMO，新增刀具後只有特定刀位卡住，應先核對什麼？」：得到核對刀具主檔與刀位對應、記錄異常條件等白話建議及來源。本輪實測 15.2～19.6 秒；見 `plain-advice.png`。這是單次觀察值範圍，並非效能保證。
- 小型模型對缺少細節的追問曾重複一般建議，因此新增保守檢查：問欄位但擷取片段未明列欄位或表格時，直接說明資料不足。實際問題「PF-INTERVIEW-DEMO 換刀卡住，刀具資料要核對哪些欄位？」顯示 0.0 秒；見 `insufficient-detail.png`。這是有限的規則檢查，不是通用語意驗證。
- 常見知識問題省去前置模型規劃，只執行一次模型整理；合併重複來源、縮短輸入和輸出。建立工單、派工仍走原本規劃與確認流程。
- 引用檢查確認來源 ID 存在並拒絕新增數值；不能保證每句改寫在語意上正確，仍須人員核對。模型判斷資料不足時不顯示其排查建議。

本輪完整測試 160 項通過（`../agent-plain-answers-tests.xml`）；後續追問與來源不足修正重跑 7 項相關測試（`../agent-plain-focused-tests.xml`），與完整測試重疊，不相加。

### 自然語言輸入更新

已移除浮動助手的設備選單與機型欄位。直接輸入「PF-INTERVIEW-DEMO 特定刀位換刀卡住，應先核對哪些資料？」後，本機 Gemma 正確帶入機型並完成 RAG 引用，這次耗時 29.2 秒；再問「那要記錄哪些資訊？」沿用相同設備與機型，耗時 22.0 秒。畫面見 `natural-language-agent.png`。這些是單次觀察值，不是延遲保證。

後端檢查抽出的機型來自使用者文字或設備登錄；機型與設備登錄不一致先追問。同機型有多台設備時，建立工單需先確認是哪台。新增上述回歸情境後，agent、CSP、本機 LLM 協定測試共 6 項通過，見 `../agent-natural-language-tests.xml`。

- 在助手選 `DEMO-INTERVIEW`，詢問「特定刀位換刀卡住，應先核對哪些資料？」。實際 Gemma 規劃知識工具，再由 RAG 選段；回覆含 S1–S3、模型名稱、可展開原文及來源紀錄。見 `rag-agent.png`。

- 接著問「把剛才建立的這張工單派給 INTERVIEW DEMO 工程師」：11.7 秒產生派工卡，正確接續剛才的工單，確認後狀態變成已指派。

- 重新載入同頁後本次登入的對話可接續，舊確認卡不恢復。桌面畫面已檢查；窄螢幕有響應式 CSS，但未在實體手機或瀏覽器裝置模擬實測。

## 重跑方式

1. 依 `docs/gemma-live-validation.md` 啟動網站與 Gemma，登入主管。
2. 任何頁面點右下角「維修助手」，直接輸入「PF-INTERVIEW-DEMO 特定刀位換刀卡住，應先核對哪些資料？」。
3. 查看回覆中的查找範圍與「白話整理」，展開引用和手冊來源；可繼續問「那要記錄哪些資訊？」。若問的細節來源不足，應補充資料後再問。
4. 輸入「幫 DEMO-INTERVIEW 建立報修，異常是【新的展示標記】換刀卡住」。先檢查確認卡，再按確認。
5. 接著輸入「把剛才這張派給 INTERVIEW DEMO 工程師」，核對工單編號，再確認。

目前是受限工具 Agent：查知識、建立報修、主管派工；核准清單、復測與結案仍使用既有流程。每次只規劃一個動作。模型沒有任意 API 或程式執行能力，所有動作都由使用者按確認後走既有後端驗權限。
